F5 BIG-IP LTM Troubleshooting

Follow traffic from the client through the BIG-IP virtual server to the backend pool member, then use connection-table, tcpdump, TLS, and iRule troubleshooting when needed.

Network Virtual Server Pool Connections tcpdump TLS Decryption iRules

1. Basic Network Checks

Interfaces

tmsh show net interface

Check

  • Interface state
  • Speed and duplex
  • Errors
  • Drops
  • Traffic counters

Trunks

tmsh show net trunk

Use this when interfaces are bundled using LACP or a static trunk.

VLAN Configuration

tmsh list net vlan

Check

  • Correct interfaces or trunks
  • Tagged versus untagged membership
  • Expected VLAN configuration

Self IPs

tmsh list net self

Check

  • Correct IP address
  • Correct VLAN
  • Port lockdown
  • Traffic-group if relevant

Routing Table

tmsh show net route

Confirm BIG-IP has a valid route toward clients, gateways, and pool members.

ARP Table

tmsh show net arp

Use this when BIG-IP cannot reach a directly connected gateway or pool member.

2. Virtual Server

Show All Virtual Servers

tmsh show ltm virtual

Check

  • Availability
  • Enabled / disabled state
  • Connections
  • Bits and packets in/out

Specific Virtual Server

tmsh show ltm virtual <virtual-server-name>

Look for

  • Availability
  • Client connections
  • Traffic counters
  • Destination VIP
  • Service port

Virtual Server Configuration

tmsh list ltm virtual <virtual-server-name> all-properties

Check

  • Destination
  • Pool
  • Source Address Translation / SNAT
  • Profiles
  • Persistence
  • iRules
  • Policies

3. Pool and Pool Members

Show Pools

tmsh show ltm pool

Specific Pool and Members

tmsh show ltm pool <pool-name> members

Check

  • Pool availability
  • Member state
  • Current connections
  • Traffic counters

Pool Configuration

tmsh list ltm pool <pool-name> all-properties

Check

  • Pool members
  • Health monitors
  • Load-balancing method
  • Priority groups if configured

Node Status

tmsh show ltm node

Use this to verify whether backend nodes themselves are marked available or unavailable.

4. Connection Troubleshooting

Connection Table

tmsh show sys connection

Use this to determine whether BIG-IP is creating a flow for the client traffic.

Filter by Client IP

tmsh show sys connection cs-client-addr <client-ip>

Filter by Virtual Server Address

tmsh show sys connection cs-server-addr <vip-address>

5. tcpdump

Enter Bash

If your SSH session opens in tmsh: 

run util bash

Basic Live Capture

CAUTION 
tcpdump -nni 0.0 -s0 host <client-IP>

Press Ctrl+C when finished.

Useful Options

  • -nn avoids hostname and service-name resolution
  • -i 0.0 captures traffic across TMM interfaces
  • -s0 captures the full packet

Client + HTTPS

tcpdump -nni 0.0 -s0 'host <client-IP> and port 443'

Pool Member Capture

tcpdump -nni 0.0 -s0 'host <pool-member-IP> and port 443'

Specific VLAN

tcpdump -nni <vlan-name> -s0 host <IP>

Save Capture to PCAP

tcpdump -nni 0.0 -s0 -w /var/tmp/app_issue.pcap 'host <client-IP> and port 443'

Workflow

1. Start capture
2. Reproduce application issue
3. Press Ctrl+C
4. Verify capture file

Verify PCAP File

ls -lh /var/tmp/app_issue.pcap

Read PCAP on BIG-IP

tcpdump -nnr /var/tmp/app_issue.pcap

Copy PCAP from BIG-IP to Windows

You can use WinSCP and download: 

/var/tmp/app_issue.pcap

Or use SCP from Windows or another workstation: 

scp admin@<BIG-IP-management-IP>:/var/tmp/app_issue.pcap .

Open the downloaded file in Wireshark.

F5 Enhanced Flow Correlation

CAUTION 
tcpdump -nni 0.0:nnn -s0 -w /var/tmp/f5_flow.pcap 'host <client-IP>'

The F5-specific :nnn modifier adds BIG-IP flow information that helps correlate traffic through TMM.

Enhanced Correlation with Peer Information

tcpdump -nni 0.0:nnnp -s0 -w /var/tmp/f5_flow.pcap 'host <client-IP>'

Purpose

This is useful when you want to correlate: 

Client-side flow

Client
  |
  v
BIG-IP VIP

        WITH

Server-side flow

BIG-IP
  |
  v
Pool Member

Capture SYN and RST

tcpdump -nni 0.0 -s0 'host <client-IP> and tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'

Look for

  • Client SYN reaching BIG-IP
  • BIG-IP response to client
  • BIG-IP SYN to pool member
  • Backend SYN-ACK
  • RST packets
  • Repeated SYN retransmissions

Useful Wireshark Filters

ip.addr == 10.10.20.55

tcp.port == 443

tcp.flags.reset == 1

tcp.analysis.retransmission

tcp.analysis.duplicate_ack

tls

http

6. TLS Capture and Session Secrets

Important Security Warning

SENSITIVE

TLS session secrets can allow captured encrypted application traffic to be decrypted. Treat PCAP and session-secret files as sensitive production data.

Modern BIG-IP TLS Capture

On supported BIG-IP versions, enable the tcpdump SSL provider: 

tmsh modify sys db tcpdump.sslprovider value enable

Then run: 

tcpdump -nni 0.0:nnn -s0 -w /var/tmp/tls_issue.pcap 'host <client-IP> and port 443' --f5 ssl

Workflow

1. Enable SSL provider
2. Start capture
3. Reproduce TLS/application issue
4. Press Ctrl+C
5. Copy PCAP to workstation
6. Analyze in Wireshark

Verify TLS Capture

ls -lh /var/tmp/tls_issue.pcap

Copy TLS Capture Off BIG-IP

scp admin@<BIG-IP-management-IP>:/var/tmp/tls_issue.pcap .

You can also use WinSCP.

Traditional Pre-Master Secret Workflow

SENSITIVE

Where supported and appropriate, a traditional workflow may use ssldump and an authorized private key. 

ssldump -r /var/tmp/app_issue.pcap -k <private-key-file> -M /var/tmp/session.pms

This creates a session-secret file: 

/var/tmp/session.pms

Transfer both: 

/var/tmp/app_issue.pcap
/var/tmp/session.pms

to the analysis workstation.

Copy Session Secret File

scp admin@<BIG-IP-management-IP>:/var/tmp/session.pms .

Wireshark TLS Decryption

1. Open PCAP in Wireshark

2. Open:
   Edit
   → Preferences
   → Protocols
   → TLS

3. Configure the TLS key-log or
   pre-master-secret file when using
   a separate session-secret file

4. Apply filters:

   tls
   http
   tcp.port == 443

5. Follow the appropriate stream

TLS Decryption Limitation

Private-key-based decryption does not work for every TLS configuration. Forward-secret cipher suites using ephemeral key exchange may require captured session secrets instead of only the server private key.

7. iRule Troubleshooting

Check iRules Attached to Virtual Server

tmsh list ltm virtual <virtual-server-name> rules

Display an iRule

tmsh list ltm rule <irule-name>

Watch LTM Log

tail -f /var/log/ltm

CLIENT_ACCEPTED Example

when CLIENT_ACCEPTED {
    log local0. "Client connected: [IP::client_addr]:[TCP::client_port]"
}

HTTP_REQUEST Example

when HTTP_REQUEST {
    log local0. "Client=[IP::client_addr] Host=[HTTP::host] URI=[HTTP::uri]"
}

SERVER_CONNECTED Example

when SERVER_CONNECTED {
    log local0. "Pool member connected: [IP::server_addr]:[TCP::server_port]"
}

SSL Session Secret Concept

SENSITIVE

BIG-IP iRules provide SSL session-related commands for advanced troubleshooting. Use session-secret logging only in controlled troubleshooting scenarios because the resulting data can permit TLS decryption. 

SSL::sessionsecret

For modern BIG-IP versions, prefer the supported tcpdump TLS capture workflow where available rather than leaving verbose session-secret logging enabled.

Logging Caution

CAUTION

Do not leave high-volume debug logging attached to busy production virtual servers. Enable it only long enough to reproduce the issue and then remove or disable it.
