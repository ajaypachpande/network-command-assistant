02 · Interfaces / Port-Channel / VLAN

Interface Status 

show interface status

Look for

  • Connected versus down/notconnect state
  • Expected VLAN or trunk state
  • Speed and duplex
  • Interface type

Detailed Interface Check 

show interface <interface>

Look for

  • Input errors
  • Output errors
  • Drops
  • Traffic counters
  • Unexpected link resets or flaps

Port-Channel Health 

show port-channel summary

Check

  • Port-channel state
  • LACP / protocol state
  • Member interfaces
  • Suspended members
  • Members operating individually instead of bundled

MAC Learning 

show mac address-table dynamic vlan <vlan-id>

If the expected MAC address is missing, work backward through VLAN membership, interface state, downstream switches, and the endpoint connection.

Start with vPC Summary 

show vpc brief

Read these fields first

  • vPC peer status
  • Peer-link status
  • Peer-keepalive status
  • Configuration consistency
  • Individual vPC/member state

Peer Keepalive 

show vpc peer-keepalive

If keepalive is unhealthy, verify the configured VRF, source/destination addresses, and the underlying Layer-3 reachability.

vPC Role 

show vpc role

Use this to understand primary/secondary role behavior during failure scenarios. The normal vPC forwarding design is still active-active.

Consistency Parameters 

show vpc consistency-parameters vpc <vpc-id>

Additional checks where supported 

show vpc consistency-parameters global
show vpc consistency-parameters interface <interface>
show vpc consistency-parameters vlans

Do not blindly copy the configuration from one peer to the other. Identify the exact mismatch first and determine which side has the intended configuration.

vPC Troubleshooting Flow

1. SUMMARY 
show vpc brief
Identify which dependency is unhealthy.
2. PEER-LINK If peer adjacency is unhealthy, verify port-channel and member interfaces.
3. KEEPALIVE If keepalive is unhealthy, verify VRF and IP reachability.
4. CONSISTENCY Identify the exact configuration mismatch.
5. MEMBER Verify port-channel, interface, VLAN, and STP state.

07 · High CPU

High CPU Troubleshooting Flow

1. CONFIRM Is CPU actually high now? 
show system resources
2. TREND Is this a short spike or sustained utilization? 
show processes cpu history
3. IDENTIFY PROCESS Which process is consuming CPU? 
show processes cpu
4. CORRELATE Match the process to the network function.

Routing churn? Interface flap? vPC/STP event? Management polling or excessive logging?

5. COLLECT EVIDENCE Correlate logs and feature state. 
show logging logfile
6. ACT Correct the verified cause or escalate with evidence.

Step 1 · Confirm CPU and Load 

show system resources

Ask

  • Is CPU actually high right now?
  • Is it higher than the normal baseline?
  • Is there application or control-plane impact?

Step 2 · Spike or Sustained? 

show processes cpu history

A short CPU spike is not automatically a fault. Focus on sustained or repeatedly abnormal utilization that correlates with service impact.

Step 3 · Identify the Process 

show processes cpu

Optional where supported 

show processes cpu sort

Sample more than once. Do not restart a process just because it appears high in one snapshot.

CPU Correlation Logic

ROUTING PROCESS Check BGP/OSPF adjacency changes, route churn, interface flaps, redistribution or topology changes.
LAYER 2 / vPC / STP Check topology changes, MAC churn, port-channel and vPC/member instability.
MANAGEMENT Check SNMP polling, telemetry, CLI load or excessive logging.
UNKNOWN / SYSTEM Collect logs and evidence before escalation.
08 · High Memory

High Memory Troubleshooting Flow

1. BASELINE Confirm the current memory state. 
show system resources
2. PROCESS MEMORY Identify which processes are using memory. 
show processes memory
3. TREND Is memory stable at a normal baseline, or continuously increasing?
4. CLASSIFY Determine whether the growth appears related to process memory, cache, kernel/system usage, or another platform-specific memory category.
5. CORRELATE Check recent software changes, configuration changes, uptime, and logs. 
show logging logfile
6. COLLECT EVIDENCE Record memory state, process usage, uptime, incident time, and recent changes.
7. ACT Use release-specific Cisco diagnostics, correct the verified cause, or escalate with evidence.

Memory Baseline 

show system resources

Process Memory Usage 

show processes memory

High overall memory utilization alone does not prove a memory leak. Trend and process ownership matter.

Questions to Ask

  • Is memory stable at this level?
  • Is memory continuously growing over hours or days?
  • Is one process growing?
  • Did the issue begin after a software, feature, or configuration change?
  • Are there process restarts or memory-related log messages?

Before a Disruptive Action

  • Record the symptom.
  • Record business/application impact.
  • Capture CPU and memory state.
  • Capture relevant interface/vPC/routing state.
  • Record recent changes.
  • Collect logs.
  • Confirm the approved recovery/change plan.

Network Engineer Troubleshooting Mindset

OBSERVE Define the symptom and impact.
MEASURE Establish objective current state.
CORRELATE Tie the abnormal state to a dependency or event.
PROVE Collect evidence before disruptive changes.
CORRECT / ESCALATE Act based on evidence, not assumptions.
