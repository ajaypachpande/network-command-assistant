2. Interface / Port-Channel / VLAN

Interface status

show interface status

Look for

  • Connected versus notconnect/down state
  • Expected VLAN or trunk behavior
  • Speed/duplex/media context

Detailed interface check

show interface <interface>

Look for

  • Input/output errors and drops
  • Link state
  • Traffic counters
  • Unexpected resets/flaps

Port-channel health

show port-channel summary

Look for

  • Port-channel state
  • Expected protocol
  • Member ports bundled/forwarding as expected
  • Suspended or individual members

Layer-2 learning

show mac address-table dynamic vlan <vlan-id>

If the expected MAC is not learned, work backward through VLAN membership, port state, downstream topology and the endpoint path.

3. vPC Troubleshooting

First command

show vpc brief

Read these fields first

  • vPC peer status
  • Peer-link status
  • Peer-keepalive status
  • Configuration consistency
  • Per-vPC/member state

Peer keepalive

show vpc peer-keepalive

If keepalive is unhealthy, verify the configured VRF, source/destination addresses and underlying reachability before changing the vPC itself.

vPC role

show vpc role

Use role information to understand primary/secondary behavior during failure conditions. Do not confuse role with normal active/active forwarding behavior.

Consistency

show vpc consistency-parameters vpc <vpc-id>

Also useful on supported releases

show vpc consistency-parameters global
show vpc consistency-parameters interface <interface>
show vpc consistency-parameters vlans

Type-1 mismatches can suspend vPC operation and must be corrected. Do not blindly copy configuration from one peer to the other. Identify the specific mismatch, decide which configuration is intended, and change the correct side under change control.

7. High CPU Troubleshooting

Step 1 - Confirm overall CPU and load

show system resources

Ask

  • Is CPU actually high now?
  • Is load above the normal baseline for this switch?
  • Is there user/service impact?

Step 2 - Determine spike versus sustained utilization

show processes cpu history

A spike alone is not automatically a fault. Investigate when utilization is sustained, repeatedly abnormal relative to baseline, tied to service impact, or owned by a persistently busy process.

Step 3 - Identify the CPU-consuming process

show processes cpu

Optional on supported releases

show processes cpu sort

Do not restart a process merely because its name is at the top once. Sample repeatedly and correlate with the time of the reported problem.

8. High Memory Troubleshooting

Step 1 - Establish memory baseline

show system resources

Step 2 - Inspect process memory

show processes memory

Cisco's Nexus 9000 troubleshooting guidance emphasizes that high-level memory utilization alone does not tell you what type of memory is high. First distinguish process memory, page cache and kernel memory before choosing advanced diagnostics.

Step 3 - Ask trend questions

  • Is memory stable at a high but normal baseline?
  • Is used memory increasing over hours/days?
  • Is one process growing continuously?
  • Did growth begin after a configuration/software/feature change?
  • Are processes restarting or OOM/service-failure messages present?

Step 4 - Correlate logs

show logging logfile

Advanced memory commands differ by release and memory type. Use Cisco's troubleshooting guide for the exact release once you determine whether the increase is process, page-cache or kernel related.

Important caution

Do not teach "memory is 80% used, therefore reboot". Linux/NX-OS memory accounting can include memory used for caches and other system functions. Evidence and trend matter more than a single percentage.

9. Evidence Collection and Escalation

Minimum evidence package

show version
show system resources
show processes cpu
show processes cpu history
show processes memory
show logging logfile
show interface status
show port-channel summary
show vpc brief

Add protocol- or feature-specific outputs only when relevant. Record the exact time of the problem so logs and CPU history can be correlated.

Before disruptive action

  • Record symptom and business impact.
  • Capture current CPU/memory/process state.
  • Capture relevant vPC/interface/routing state.
  • Record recent changes.
  • Save logs/evidence.
  • Confirm the approved recovery/change plan.
