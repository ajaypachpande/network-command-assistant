Route 53 Hosted Zone and Resume Subdomain Lab

Learn how Terraform can describe a public Route 53 hosted zone for ajaynetwork.com and create the resume.ajaynetwork.com DNS record.

Educational Mode

This page is for learning and knowledge sharing only. The Network Command Assistant does not execute terraform apply or connect to an AWS account.

Important

Do not place AWS access keys, secret keys, session tokens, passwords, or other credentials inside Terraform files committed to Git.

Important DNS Concept 

Domain Registration
        !=
Route 53 Hosted Zone
        !=
DNS Record

These are related, but they are different operations.

  • Domain registration controls ownership of the domain name.
  • Route 53 hosted zone stores DNS records for the domain.
  • DNS records define names such as resume.ajaynetwork.com.

DNS Authority and Delegation

Creating a hosted zone in Route 53 does not automatically make Route 53 authoritative for the public domain. 

Registrar / Parent DNS
        |
        | delegates using NS records
        v
Route 53 Hosted Zone
ajaynetwork.com
        |
        v
DNS records become publicly authoritative

For this learning example, assume Route 53 will be authoritative for ajaynetwork.com.

Existing DNS Warning

If ajaynetwork.com already uses Cloudflare or another DNS provider, do not change production name servers simply to test this example.

2. provider.tf

The provider block tells the AWS Provider which region to use.

3. variables.tf

  description = "Public Route 53 hosted zone."
  type        = string

  description = "Resume subdomain name."
  type        = string

4. main.tf

This is the main infrastructure definition.

main.tf 
# ==========================================================
# ROUTE 53 PUBLIC HOSTED ZONE
# ==========================================================

resource "aws_route53_zone" "ajaynetwork" {
  name = var.domain_name

  tags = {
    Name        = "ajaynetwork.com"
    Environment = "learning"
    ManagedBy   = "Terraform"
  }
}


# ==========================================================
# RESUME SUBDOMAIN
# resume.ajaynetwork.com
# ==========================================================

resource "aws_route53_record" "resume" {
  zone_id = aws_route53_zone.ajaynetwork.zone_id

  name = "${var.resume_hostname}.${var.domain_name}"

  type = "CNAME"

  ttl = 300

  records = [
    var.resume_target
  ]
}

How Terraform Understands the Dependency 

aws_route53_zone.ajaynetwork
            |
            | provides zone_id
            v
aws_route53_record.resume
            |
            v
resume.ajaynetwork.com

Terraform sees this expression: 

zone_id = aws_route53_zone.ajaynetwork.zone_id

That creates an implicit dependency. Terraform knows the hosted zone must exist before the DNS record can reference its zone ID.

What If the Resume Site Uses an IP Address?

A CNAME points to another hostname. If your target is an IPv4 address instead, use an A record.

A RECORD EXAMPLE 
resource "aws_route53_record" "resume" {
  zone_id = aws_route53_zone.ajaynetwork.zone_id

  name = "resume.${var.domain_name}"

  type = "A"

  ttl = 300

  records = [
    "192.0.2.10"
  ]
}

The address above is documentation-only.

A Record vs CNAME 

A RECORD

resume.ajaynetwork.com
        |
        v
IPv4 address


CNAME

resume.ajaynetwork.com
        |
        v
another hostname

Choose the DNS record type based on what the application endpoint actually provides.
